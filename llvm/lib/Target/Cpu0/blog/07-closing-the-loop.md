# Closing the Loop: C++ Features, Atomics, and Verifying on a Verilog CPU

*Part 7 of "Building an LLVM Backend From Scratch" — using the Cpu0 architecture as a case study to explore LLVM's backend architecture.*

## The Last Mile

Posts 1 through 6 built a backend that compiles C to assembly, generates object files, and round-trips through an assembler and disassembler. That covers the bread and butter of a backend -- arithmetic, control flow, function calls, globals, relocations.

But a modern backend needs more. C++ programs throw exceptions. Multi-threaded programs access thread-local variables. Lock-free data structures use atomic operations. And to be confident that 12,260 lines of backend code are correct, it helps to run programs on an actual CPU -- even a simulated one.

This post covers the final chapters of the Cpu0 backend: **exception handling**, **thread-local storage**, **atomic operations with LL/SC loops**, and **verification on a Verilog RTL simulator**. Along the way, we'll encounter two bugs that were invisible to the compiler's test suite but immediately caught by hardware simulation.

## Exception Handling

C++ exception handling (`throw`/`catch`) compiles down to LLVM IR's `invoke`/`landingpad` instructions. The backend's job is to generate the metadata tables that the runtime unwinder needs to find catch handlers and clean up stack frames.

### What the Backend Must Do

Exception handling doesn't require new instructions -- it requires **metadata**. Specifically:

- **`.gcc_except_table`** -- Per-function tables that map PC ranges to landing pads and type filters. Generated by LLVM's `EHStreamer` using information from `MachineFunction`.
- **`.eh_frame`** -- DWARF Call Frame Information (CFI) that tells the unwinder how to restore registers and unwind the stack at any PC. Generated from the `DwarfRegNumForCFI` mappings we provide.
- **`EH_RETURN`** lowering -- The `llvm.eh.return` intrinsic, used to resume execution at an exception handler.

The backend enables DWARF-based exception handling in `Cpu0MCAsmInfo.cpp`:

```cpp
Cpu0MCAsmInfo::Cpu0MCAsmInfo(const Triple &TheTriple) {
  // ...
  SupportsDebugInformation = true;
  ExceptionsType = ExceptionHandling::DwarfCFI;
  DwarfRegNumForCFI = true;
}
```

`DwarfRegNumForCFI = true` means we use DWARF register numbers in CFI directives (`.cfi_offset`, `.cfi_def_cfa_register`). The register numbering is defined in `Cpu0RegisterInfo.td`.

### Lowering EH_RETURN

The `EH_RETURN` ISD node takes a stack offset and a handler address. Our lowering copies them into fixed physical registers and emits a custom `Cpu0ISD::EH_RETURN` node:

```cpp
SDValue Cpu0TargetLowering::lowerEH_RETURN(SDValue Op,
                                           SelectionDAG &DAG) const {
  MachineFunction &MF = DAG.getMachineFunction();
  Cpu0FunctionInfo *Cpu0FI = MF.getInfo<Cpu0FunctionInfo>();
  Cpu0FI->setCallsEhReturn();

  SDValue Chain = Op.getOperand(0);
  SDValue Offset = Op.getOperand(1);
  SDValue Handler = Op.getOperand(2);
  SDLoc DL(Op);

  // Store stack offset in V1, store jump target in V0.
  unsigned OffsetReg = Cpu0::V1;
  unsigned AddrReg = Cpu0::V0;
  Chain = DAG.getCopyToReg(Chain, DL, OffsetReg, Offset, SDValue());
  Chain = DAG.getCopyToReg(Chain, DL, AddrReg, Handler, Chain.getValue(1));
  return DAG.getNode(Cpu0ISD::EH_RETURN, DL, MVT::Other, Chain,
                     DAG.getRegister(OffsetReg, MVT::i32),
                     DAG.getRegister(AddrReg,
                       getPointerTy(MF.getDataLayout())),
                     Chain.getValue(1));
}
```

The register choice (`V0` for handler, `V1` for offset) follows MIPS convention. The `setCallsEhReturn()` flag tells the prologue/epilogue emitter to save and restore additional state.

### The Landing Pad Table Structure

When a C++ exception is thrown, the runtime unwinder walks the stack looking for a matching catch handler. For each stack frame, it consults the **LSDA** (Language-Specific Data Area), which is stored in the `.gcc_except_table` section:

```
.gcc_except_table structure per function:
  LSDA header
    lpstart_encoding    — how to encode landing pad addresses
    ttype_encoding      — how to encode type info entries
    ttype_offset        — offset to type info table (end of the call site table)

  Call site table (one entry per potentially-throwing code range):
    cs_start            — start of code region (relative to function start)
    cs_len              — length of code region
    cs_lp               — landing pad address (0 = no handler, just cleanup)
    cs_action           — index into action table (0 = cleanup only)

  Action table (per (landing pad, type filter) pair):
    action              — type info index (positive), cleanup (0), or filter (-n)
    next_action         — chain to next action for this landing pad

  Type info table (catch types, in reverse order):
    typeinfo ptr        — pointer to RTTI for each catchable type
```

The backend doesn't construct this table manually. LLVM's `EHStreamer` in `CodeGen/AsmPrinter/EHStreamer.cpp` does the heavy lifting. The backend only needs to:
1. Emit CFI directives in the prologue/epilogue (so the unwinder can find saved registers)
2. Mark which instructions can throw with `MachineInstr` metadata
3. Declare the `DwarfRegNum` mappings for all registers

When you set `ExceptionsType = ExceptionHandling::DwarfCFI`, LLVM automatically generates the `.eh_frame` and `.gcc_except_table` sections from the MachineFunction metadata.

The `.eh_frame` section is generated from the CFI instructions emitted in every function prologue and epilogue. When the frame lowering emits `CFI_INSTRUCTION` pseudo-nodes (wrapping `MCCFIInstruction` objects), the AsmPrinter serializes them as DWARF directives:

```asm
foo:
    .cfi_startproc              # mark start of function for unwinder
    addiu $sp, $sp, -16
    .cfi_def_cfa_offset 16      # CFA is now $sp + 16
    st $lr, 12($sp)
    .cfi_offset 14, -4          # DWARF reg 14 ($lr) saved at CFA-4
    st $fp, 8($sp)
    .cfi_offset 12, -8          # DWARF reg 12 ($fp) saved at CFA-8
    # ... function body ...
    addiu $sp, $sp, 16
    .cfi_def_cfa_offset 0       # CFA restored to $sp + 0
    ret $lr
    .cfi_endproc                # mark end of function
```

The DWARF register numbers 14 and 12 come from the `DwarfRegNum<[14]>` and `DwarfRegNum<[12]>` annotations in `Cpu0RegisterInfo.td`. If these annotations were wrong or missing, GDB and libunwind would read the wrong register values when unwinding, producing incorrect backtraces and potentially crashing exception-based cleanup code.

## Thread-Local Storage (TLS)

```
Model             When to use                   Assembly sequence                      Cost
──────────────────────────────────────────────────────────────────────────────────────────────
General Dynamic   Any DSO; var may be in        .tlsgd                                 Function call
(GD)              another DSO                   addiu $a0,$gp,%tlsgd(x)                per access
                                                jalr __tls_get_addr

Local Dynamic     Var in same DSO;              .tlsldm + jalr __tls_get_addr          One call/module
(LD)              multiple TLS vars             addiu $v0,$v0,%dtprel_lo(x)            + offset/var

Initial Exec      Var in main exe,              ld $t0, %gottprel(x)($gp)              GOT load,
(IE)              known at load time            addu $t0, $t0, $tp                     no call

Local Exec        Var in main exe,              lui $t0, %tprel_hi(x)                  Direct offset,
(LE)              static link                   addiu $t0, $t0, %tprel_lo(x)           fastest

GD → LD → IE → LE: progressively less flexible, progressively faster
```

Thread-local variables (`__thread` in C, `thread_local` in C++) require special relocation sequences because each thread has its own copy of the variable. The linker and runtime loader cooperate to resolve the variable's address, and different deployment scenarios need different strategies.

Cpu0 supports all four TLS models defined by the ELF ABI. The choice of model depends on deployment scenario:

| Model | When to use | Relocation types |
|-------|------------|-----------------|
| **LocalExec** | Static executables, variable defined in the same executable | `%tp_hi`, `%tp_lo` |
| **InitialExec** | Shared lib, but loaded at startup (not dlopen) | `%gottprel` |
| **LocalDynamic** | Shared lib, variable defined locally, dlopen possible | `%tlsldm`, `%dtp_hi`, `%dtp_lo` |
| **GeneralDynamic** | Shared lib, variable defined elsewhere, dlopen | `%tlsgd` |

The compiler picks the model based on visibility and linkage flags. A backend must implement all four because code may link against objects compiled with different models.

### LocalExec -- Known offset, static linking

The simplest model. The variable's offset from the thread pointer (TP) is known at link time:

```cpp
// model == TLSModel::LocalExec
SDValue TGAHi =
    DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Cpu0II::MO_TP_HI);
SDValue TGALo =
    DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Cpu0II::MO_TP_LO);
SDValue Hi = DAG.getNode(Cpu0ISD::Hi, DL, PtrVT, TGAHi);
SDValue Lo = DAG.getNode(Cpu0ISD::Lo, DL, PtrVT, TGALo);
Offset = DAG.getNode(ISD::ADD, DL, PtrVT, Hi, Lo);
```

This generates:
```asm
lui   $r2, %tp_hi(t_le)
addiu $r2, $r2, %tp_lo(t_le)
addu  $r2, $r2, $tp          ; add thread pointer
ld    $r2, 0($r2)
```

### InitialExec -- GOT-indirect, static linking

The variable's offset is loaded from the GOT at runtime:

```cpp
// model == TLSModel::InitialExec
SDValue TGA =
    DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Cpu0II::MO_GOTTPREL);
TGA =
    DAG.getNode(Cpu0ISD::Wrapper, DL, PtrVT, getGlobalReg(DAG, PtrVT), TGA);
Offset =
    DAG.getLoad(PtrVT, DL, DAG.getEntryNode(), TGA, MachinePointerInfo());
```

This generates a GOT load with the `%gottprel` relocation.

### GeneralDynamic -- Full dynamic linking

The most general (and slowest) model. Calls `__tls_get_addr` at runtime:

```cpp
if (model == TLSModel::GeneralDynamic || model == TLSModel::LocalDynamic) {
  unsigned Flag = (model == TLSModel::LocalDynamic) ? Cpu0II::MO_TLSLDM
                                                    : Cpu0II::MO_TLSGD;
  SDValue TGA = DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Flag);
  SDValue Argument =
      DAG.getNode(Cpu0ISD::Wrapper, DL, PtrVT, getGlobalReg(DAG, PtrVT), TGA);
  SDValue TlsGetAddr = DAG.getExternalSymbol("__tls_get_addr", PtrVT);
  // ... set up call
  std::pair<SDValue, SDValue> CallResult = LowerCallTo(CLI);
  SDValue Ret = CallResult.first;
  if (model != TLSModel::LocalDynamic)
    return Ret;
```

GeneralDynamic wraps the symbol address with `%tlsgd` and calls `__tls_get_addr`. The runtime linker resolves the actual address.

### LocalDynamic -- Optimized dynamic linking

Like GeneralDynamic, but adds a local DTP offset after the call:

```cpp
  SDValue TGAHi =
      DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Cpu0II::MO_DTP_HI);
  SDValue Hi = DAG.getNode(Cpu0ISD::Hi, DL, PtrVT, TGAHi);
  SDValue TGALo =
      DAG.getTargetGlobalAddress(GV, DL, PtrVT, 0, Cpu0II::MO_DTP_LO);
  SDValue Lo = DAG.getNode(Cpu0ISD::Lo, DL, PtrVT, TGALo);
  SDValue Add = DAG.getNode(ISD::ADD, DL, PtrVT, Hi, Ret);
  return DAG.getNode(ISD::ADD, DL, PtrVT, Add, Lo);
```

The `__tls_get_addr` call returns the base of the module's TLS block, and the `%dtp_hi`/`%dtp_lo` relocations add the variable's offset within that block.

Our test covers all four models:

```llvm
; --- LocalExec TLS model (static) ---
; RUN: llc -march=cpu0 -relocation-model=static -filetype=asm < %s \
; RUN:   | FileCheck %s --check-prefix=LOCALEXEC

@t_le = thread_local(localexec) global i32 0, align 4
define i32 @read_tls_localexec() nounwind {
; LOCALEXEC-LABEL: read_tls_localexec:
; LOCALEXEC: %tp_hi(t_le)
; LOCALEXEC: %tp_lo(t_le)
  %val = load i32, i32* @t_le, align 4
  ret i32 %val
}
```

## Atomics and LL/SC Loops

```
        ┌──────────────────────────────────────┐
        │             Entry block              │
        └──────────────────┬───────────────────┘
                           ▼
        ┌──────────────────────────────────────┐◀─────┐
        │  LL oldval, 0(ptr)                   │      │
        │  (Load-Linked: reserve cache line)   │      │
        └──────────────────┬───────────────────┘      │
                           ▼                          │ retry
        ┌──────────────────────────────────────┐      │
        │  newval = oldval OP operand          │      │
        └──────────────────┬───────────────────┘      │
                           ▼                          │
        ┌──────────────────────────────────────┐      │
        │  SC success, newval, 0(ptr)          │      │
        │  (Store-Cond: fails if line touched) │      │
        └──────────────────┬───────────────────┘      │
                           ▼                          │
                   ┌───────────────┐   No (SC failed) ┘
                   │ success == 1? │──────────────────▶
                   └───────┬───────┘
                           │ Yes
                           ▼
        ┌──────────────────────────────────────┐
        │          Exit block (done)           │
        └──────────────────────────────────────┘
```

Atomic operations are where the backend gets interesting. LLVM IR has `atomicrmw` (atomic read-modify-write) and `cmpxchg` (compare-and-swap) instructions. On architectures without hardware CAS instructions, these must be lowered to **load-linked/store-conditional (LL/SC)** loops.

Cpu0 provides two special instructions:
- **`LL` (load-linked)**: Loads a word and starts a hardware reservation on the address
- **`SC` (store-conditional)**: Stores a word only if the reservation is still valid; returns 1 on success, 0 on failure

### The emitAtomicBinary Pattern

Every `atomicrmw` on `i32` follows the same loop pattern. The `emitAtomicBinary()` method constructs it from `MachineInstr`s at the pseudo-instruction expansion stage:

```cpp
MachineBasicBlock *Cpu0TargetLowering::emitAtomicBinary(MachineInstr &MI,
                                                        MachineBasicBlock *BB,
                                                        unsigned Size,
                                                        unsigned BinOpcode,
                                                        bool Nand) const {
  // ... setup ...

  // Create loopMBB and exitMBB
  MachineBasicBlock *loopMBB = MF->CreateMachineBasicBlock(LLVM_BB);
  MachineBasicBlock *exitMBB = MF->CreateMachineBasicBlock(LLVM_BB);

  BB->addSuccessor(loopMBB);
  loopMBB->addSuccessor(loopMBB);   // loop back edge
  loopMBB->addSuccessor(exitMBB);   // exit edge

  //  loopMBB:
  //    ll oldval, 0(ptr)
  //    <binop> storeval, oldval, incr
  //    sc success, storeval, 0(ptr)
  //    beq success, $zero, loopMBB
  BB = loopMBB;
  BuildMI(BB, DL, TII->get(LL), OldVal).addReg(Ptr).addImm(0);
  if (Nand) {
    //  and andres, oldval, incr
    //  nor storeval, $zero, andres    ; storeval = ~(oldval & incr)
    BuildMI(BB, DL, TII->get(AND), AndRes).addReg(OldVal).addReg(Incr);
    BuildMI(BB, DL, TII->get(NOR), StoreVal).addReg(ZERO).addReg(AndRes);
  } else if (BinOpcode) {
    //  <binop> storeval, oldval, incr
    BuildMI(BB, DL, TII->get(BinOpcode), StoreVal)
        .addReg(OldVal).addReg(Incr);
  } else {
    StoreVal = Incr;  // atomic swap: just store the new value
  }
  BuildMI(BB, DL, TII->get(SC), Success)
      .addReg(StoreVal).addReg(Ptr).addImm(0);
  BuildMI(BB, DL, TII->get(BEQ))
      .addReg(Success).addReg(ZERO).addMBB(loopMBB);
```

The loop is simple: load-linked, modify, store-conditional, retry if failed. But notice the three code paths:

1. **Normal binary op** (`BinOpcode != 0`, `Nand == false`): Insert a single `<binop>` between LL and SC. Used for `add`, `sub`, `and`, `or`, `xor`.
2. **NAND** (`Nand == true`): Insert `AND` + `NOR` to compute `~(oldval & incr)`.
3. **Swap** (`BinOpcode == 0`, `Nand == false`): Skip the binary op entirely -- just store the incoming value.

This method is used for all `i32` atomic operations, parameterized by `BinOpcode`:

```cpp
case Cpu0::ATOMIC_LOAD_ADD_I32:
  return emitAtomicBinary(MI, BB, 4, Cpu0::ADDu);
case Cpu0::ATOMIC_LOAD_AND_I32:
  return emitAtomicBinary(MI, BB, 4, Cpu0::AND);
case Cpu0::ATOMIC_LOAD_NAND_I32:
  return emitAtomicBinary(MI, BB, 4, 0, true);
case Cpu0::ATOMIC_SWAP_I32:
  return emitAtomicBinary(MI, BB, 4, 0);
```

### Compare-and-Swap (cmpxchg)

`cmpxchg` is structurally different -- it has two loops. The `emitAtomicCmpSwap()` method builds a two-block loop:

```cpp
// loop1MBB:
//   ll dest, 0(ptr)
//   bne dest, oldval, exitMBB       ; if loaded != expected, bail
BB = loop1MBB;
BuildMI(BB, DL, TII->get(LL), Dest).addReg(Ptr).addImm(0);
BuildMI(BB, DL, TII->get(BNE))
    .addReg(Dest).addReg(OldVal).addMBB(exitMBB);

// loop2MBB:
//   sc success, newval, 0(ptr)
//   beq success, $zero, loop1MBB    ; if SC failed, retry
BB = loop2MBB;
BuildMI(BB, DL, TII->get(SC), Success)
    .addReg(NewVal).addReg(Ptr).addImm(0);
BuildMI(BB, DL, TII->get(BEQ))
    .addReg(Success).addReg(ZERO).addMBB(loop1MBB);
```

The first block loads the current value and compares it. If it doesn't match the expected value, we exit immediately. If it matches, we try to store the new value. If SC fails (another thread intervened), we retry the whole thing.

### Memory Ordering: Fences

LLVM IR specifies memory ordering (`monotonic`, `acquire`, `release`, `seq_cst`). Cpu0 maps all non-relaxed orderings to the `SYNC` instruction:

```cpp
SDValue Cpu0TargetLowering::lowerATOMIC_FENCE(SDValue Op,
                                              SelectionDAG &DAG) const {
  unsigned SType = 0;
  SDLoc DL(Op);
  return DAG.getNode(Cpu0ISD::Sync, DL, MVT::Other, Op.getOperand(0),
                     DAG.getConstant(SType, DL, MVT::i32));
}
```

For `seq_cst` atomics, the sync is emitted both before and after the LL/SC loop. The test verifies this:

```llvm
define i32 @atomic_xor_i32(i32* %ptr, i32 %val) nounwind {
; CHECK-LABEL: atomic_xor_i32:
; CHECK: sync
; CHECK: ll
; CHECK: xor
; CHECK: sc
; CHECK: sync
  %old = atomicrmw xor i32* %ptr, i32 %val seq_cst
  ret i32 %old
}
```

## How Atomics Reach the Backend: The AtomicExpand Pass

Before SelectionDAG ever sees an atomic operation, an IR-level pass transforms it into a form the backend can handle. This is the **AtomicExpand pass**, registered in `Cpu0TargetMachine.cpp`:

```cpp
// From Cpu0TargetMachine.cpp
void Cpu0PassConfig::addIRPasses() {
  TargetPassConfig::addIRPasses();
  addPass(createAtomicExpandPass());  // Runs before ISel
}
```

The pass queries the target lowering to decide how to handle each atomic operation. For Cpu0, `shouldExpandAtomicRMWInIR()` returns `AtomicExpansionKind::LLSC` for all `atomicrmw` operations, telling the pass to expand them into `llvm.llsc.load` / `llvm.llsc.store` intrinsic sequences at the IR level.

But wait — the backend's `EmitInstrWithCustomInserter` expands pseudo-instructions *at the MachineInstr level*, not at IR level. Why both?

The answer is that there are two expansion strategies, and Cpu0 uses the **MachineInstr expansion path**:

1. **IR-level expansion** (via AtomicExpand): Emits LLVM IR `cmpxchg` loops using IR branch instructions. The resulting IR then goes through the normal ISel pipeline.

2. **MachineInstr expansion** (via `EmitInstrWithCustomInserter`): The backend emits an atomic pseudo-instruction during ISel, then expands it to a real LL/SC loop at the MachineInstr level after register allocation.

Cpu0 uses path 2. The AtomicExpand pass transforms `atomicrmw` into `cmpxchg` at IR level only for operations that truly need it (like `nand`, which has no direct analog), but most operations are marked as `Custom` in `EmitInstrWithCustomInserter`:

```cpp
// From Cpu0ISelLowering.cpp
MachineBasicBlock *
Cpu0TargetLowering::EmitInstrWithCustomInserter(MachineInstr &MI,
                                                MachineBasicBlock *BB) const {
  switch (MI.getOpcode()) {
  case Cpu0::ATOMIC_LOAD_ADD_I32:
    return emitAtomicBinary(MI, BB, 4, Cpu0::ADDu);
  case Cpu0::ATOMIC_LOAD_SUB_I32:
    return emitAtomicBinary(MI, BB, 4, Cpu0::SUBu);
  case Cpu0::ATOMIC_LOAD_AND_I32:
    return emitAtomicBinary(MI, BB, 4, Cpu0::AND);
  case Cpu0::ATOMIC_LOAD_OR_I32:
    return emitAtomicBinary(MI, BB, 4, Cpu0::OR);
  case Cpu0::ATOMIC_LOAD_XOR_I32:
    return emitAtomicBinary(MI, BB, 4, Cpu0::XOR);
  case Cpu0::ATOMIC_LOAD_NAND_I32:
    return emitAtomicBinary(MI, BB, 4, 0, true);  // Nand = true
  case Cpu0::ATOMIC_SWAP_I32:
    return emitAtomicBinary(MI, BB, 4, 0);        // No binop = swap
  case Cpu0::ATOMIC_CMP_SWAP_I32:
    return emitAtomicCmpSwap(MI, BB, 4);
  // Sub-word variants:
  case Cpu0::ATOMIC_LOAD_ADD_I8:  return emitAtomicBinaryPartword(MI, BB, 1, Cpu0::ADDu);
  case Cpu0::ATOMIC_LOAD_ADD_I16: return emitAtomicBinaryPartword(MI, BB, 2, Cpu0::ADDu);
  // ... etc.
  }
}
```

The `emitAtomicBinary` family of methods **creates new MachineBasicBlocks** (the loop body and exit) and inserts them into the function's CFG. This is the `EmitInstrWithCustomInserter` mechanism in its most powerful form: one pseudo-instruction expands into a multi-block graph transformation.

The AtomicExpand pass handles one case that can't be done at the MachineInstr level: converting unsupported atomic widths. If the target doesn't support `i64` atomics (Cpu0 doesn't), AtomicExpand can synthesize them from `i32` operations before ISel sees them.

## Sub-Word Atomics: Byte Masking for i8/i16

```
32-bit word at aligned address:
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ byte3[31:24]│ byte2[23:16]│ byte1[15:8] │ byte0[7:0]  │
└─────────────┴─────────────┴─────────────┴─────────────┘
                                  ↑ example: i8 atomic on byte1

  Big-endian:    byte1 shift = 16
  Little-endian: byte1 shift = 8

Steps for sub-word i8 atomic add:
  1. Align ptr to 4-byte boundary
  2. Compute shift (endian-dependent)
  3. LL on full 32-bit aligned word
  4. Isolate byte:   (word >> shift) & 0xFF
  5. Compute new byte value
  6. Mask in:        (word & ~mask) | (newbyte << shift)
  7. SC full 32-bit word back to aligned address
  8. Retry from step 3 if SC fails
```

Cpu0's LL/SC operates on 32-bit words only. To atomically modify a single byte or halfword, the backend must synthesize a **sub-word atomic** using bit masking. This is one of the most intricate parts of the entire backend.

The idea: align the address to a word boundary, compute a mask for the target byte/halfword, and perform the LL/SC on the full word while preserving the surrounding bytes.

Here's the setup code from `emitAtomicBinaryPartword()`:

```cpp
//  thisMBB:
//    addiu   masklsb2,$zero,-4             # 0xfffffffc
//    and     alignedaddr,ptr,masklsb2      # word-align the pointer
//    andi    ptrlsb2,ptr,3                 # byte offset within word
//    sll     shiftamt,ptrlsb2,3            # convert to bit offset
//    ori     maskupper,$zero,255           # 0xff for i8 (or 0xffff for i16)
//    sll     mask,maskupper,shiftamt       # position the mask
//    nor     mask2,$zero,mask              # mask2 = ~mask
//    sll     incr2,incr,shiftamt           # position the increment
```

For **big-endian**, there's an extra XOR step that flips the byte offset:

```cpp
if (Subtarget.isLittle()) {
  BuildMI(BB, DL, TII->get(Cpu0::SHL), ShiftAmt)
      .addReg(PtrLSB2).addImm(3);
} else {
  unsigned Off = RegInfo.createVirtualRegister(RC);
  BuildMI(BB, DL, TII->get(Cpu0::XORi), Off)
      .addReg(PtrLSB2)
      .addImm((Size == 1) ? 3 : 2);
  BuildMI(BB, DL, TII->get(Cpu0::SHL), ShiftAmt)
      .addReg(Off).addImm(3);
}
```

On little-endian, byte 0 is at the lowest address and the lowest bit position -- so `ptrlsb2 * 8` gives the correct shift. On big-endian, byte 0 is at the lowest address but the *highest* bit position within the word, so we XOR with 3 (for bytes) or 2 (for halfwords) to reverse the index.

Then the LL/SC loop:

```cpp
//  loopMBB:
//    ll      oldval,0(alignedaddr)
//    <binop> binopres,oldval,incr2        # operate on shifted value
//    and     newval,binopres,mask          # isolate modified bits
//    and     maskedoldval0,oldval,mask2    # preserve surrounding bits
//    or      storeval,maskedoldval0,newval # combine
//    sc      success,storeval,0(alignedaddr)
//    beq     success,$zero,loopMBB
```

After the loop succeeds, the result must be extracted and sign-extended:

```cpp
//  sinkMBB:
//    and     maskedoldval1,oldval,mask    # extract the old sub-word value
//    srl     srlres,maskedoldval1,shiftamt # shift back to position 0
//    sign_extend dest,srlres              # SHL + SRA pair for sign extension
```

Our test exercises both endiannesses. The big-endian test expects the XOR byte-swap:

```llvm
define i8 @atomic_add_i8(i8* %ptr, i8 %val) nounwind {
; CHECK-LABEL: atomic_add_i8:
; CHECK: addiu {{.*}}, $zero, -4
; CHECK: and
; CHECK: andi {{.*}}, 3
; BE:    xori {{.*}}, 3
; CHECK: ori {{.*}}, 255
; CHECK: shlv
; CHECK: nor
; CHECK: ll
; CHECK: addu
; CHECK: sc
```

The little-endian test uses `CHECK-NOT` to verify the byte-swap does **not** appear:

```llvm
define i8 @atomic_add_i8_le(i8* %ptr, i8 %val) nounwind {
; CHECK-LABEL: atomic_add_i8_le:
; CHECK: addiu {{.*}}, $zero, -4
; CHECK: and
; CHECK: andi {{.*}}, 3
; CHECK-NOT: xori
; CHECK: shl
; CHECK: ori {{.*}}, 255
```

## War Story: NOR, Not XOR -- The NAND Bug

During development, we initially followed the reference implementation at `lbd/lbdex/Cpu0/` for the NAND atomic operation. NAND computes `~(oldval & incr)` -- the bitwise NOT of the AND result.

The reference code used `XOR $ZERO, reg` for the bitwise NOT. This looks plausible -- XOR with an all-bits pattern would flip all bits. But `$ZERO` is the zero register, and `XOR 0, x = x`. It's the **identity operation**, not a bitwise NOT.

The correct instruction is `NOR $ZERO, reg`, because `NOR(0, x) = ~(0 | x) = ~x`.

This bug was invisible in the reference implementation because its test suite didn't verify the actual instruction used for the NOT -- it only checked that the LL/SC loop structure was present. Our test catches it explicitly:

```llvm
; NAND = ~(oldval & incr). Must use NOR for the NOT, not XOR.
define i32 @atomic_nand_i32(i32* %ptr, i32 %val) nounwind {
; CHECK-LABEL: atomic_nand_i32:
; CHECK: ll
; CHECK: and
; CHECK: nor
; CHECK: sc
  %old = atomicrmw nand i32* %ptr, i32 %val monotonic
  ret i32 %old
}
```

The `CHECK: nor` line is what catches the bug. If the backend emitted `xor` instead, this test would fail. The lesson: **test the distinguishing instruction, not just the loop structure**.

This same bug affected sub-word NAND and the mask inversion in `emitAtomicBinaryPartword()`, where `NOR $ZERO, mask` computes the inverted mask `~mask`. Both were fixed to use `NOR` throughout.

## War Story: SetCC_I Encoding Bug -- Found by Verilog, Not by LLVM

The second bug was more subtle and more revealing about the limits of compiler-level testing.

Cpu0's `SLTi` (set-less-than immediate) and `SLTiu` instructions are Format L instructions -- they take a register and a 16-bit immediate:

```
Format L: <|opcode|ra|rb|imm16|>
```

But in our initial implementation, these instructions were incorrectly defined using Format A encoding (the 3-register format). The LLVM test suite didn't catch this because:

1. The instruction selector produced correct `MCInst` objects (the operands were right)
2. The assembly printer formatted them correctly (it uses operand indices, not bit fields)
3. The disassembler decoded them correctly (TableGen regenerated consistent but wrong tables)

The only thing wrong was the **binary encoding** -- the bits in the object file put the immediate in the wrong position. And the only way to catch a wrong binary encoding is to execute the binary on something that interprets the bits.

The Verilog RTL simulator caught this immediately: programs using `SLTi` would produce wrong comparison results, leading to incorrect branches. The fix was to change the instruction definition from FA to FL format.

## Verilog Verification

```
C source ──[clang]──▶ LLVM IR ──[llc]──▶ Cpu0 binary ──[load]──▶ Verilog CPU ──[simulate]──▶ stdout ──┐
                                          (.hex file)              (Icarus Verilog)                   │
                                                                                    diff vs expected ◀┘
                                                                                    ✓ must match

Test matrix (all 4 configurations must produce correct output):
  ┌────────────────────────────┬────────────────────────────┐
  │  Cpu032I  + Big-Endian     │  Cpu032I  + Little-Endian  │
  ├────────────────────────────┼────────────────────────────┤
  │  Cpu032II + Big-Endian     │  Cpu032II + Little-Endian  │
  └────────────────────────────┴────────────────────────────┘
  Run: verilog/input/build-run_backend.sh cpu032I|cpu032II eb|el
```

The ultimate correctness test for a backend isn't assembling and disassembling -- it's **executing programs on the target architecture**. The Cpu0 project includes a Verilog RTL model of the CPU that can run compiled programs.

### The Verilog CPU Model

The CPU model lives in `verilog/cpu0.v` and implements the full Cpu0 ISA in about 1,000 lines of SystemVerilog:

```verilog
module cpu0(input clock, reset, input [2:0] itype, output reg [2:0] tick,
            output reg [31:0] ir, pc, mar, mdr, inout [31:0] dbus,
            output reg m_en, m_rw, output reg [1:0] m_size,
            input cfg);
  reg signed [31:0] R [0:15];
  reg signed [31:0] C0R [0:1]; // co-processor 0 register
  reg [7:0] op;
  reg [3:0] a, b, c;
  reg signed [31:0] c12, c16, c24, Ra, Rb, Rc, pc0;
  reg [31:0] uc16, URa, URb, URc, HI, LO, CF, tmp;
  reg [63:0] cycles;
```

It has 16 GPRs, 2 coprocessor-0 registers (PC and EPC), HI/LO for multiply/divide, and a configurable endianness flag. It decodes instructions from memory, executes them cycle by cycle, and writes results back.

### The Test Pipeline

The verification script (`verilog/input/build-run_backend.sh`) runs this pipeline:

```bash
# 1. Compile C++ to LLVM bitcode (using clang with MIPS target)
$CLANG -target mips-unknown-linux-gnu -c ch_run_backend.cpp \
  -emit-llvm -o ch_run_backend.bc

# 2. Lower to Cpu0 object file
${TOOLDIR}/llc -march=cpu0${ENDIAN} -mcpu=${CPU} -relocation-model=static \
  -filetype=obj ch_run_backend.bc -o ch_run_backend.cpu0.o

# 3. Extract raw .text section and convert to hex for Verilog $readmemh
${TOOLDIR}/llvm-objcopy -O binary --only-section=.text \
  ch_run_backend.cpu0.o ch_run_backend.text.bin
xxd -p ch_run_backend.text.bin | fold -w2 | \
  awk '{printf "%s%s", $0, (NR%4==0 ? "\n" : " ")}' > ../cpu0.hex

# 4. Configure endianness for simulator
ENDIAN=$(llvm-readobj -h ch_run_backend.cpu0.o | grep "DataEncoding" | awk '{print $2}')
if [ $LE == "true" ] ; then
  echo "1   /* 0: big ENDIAN, 1: little ENDIAN */" > ../cpu0.config
else
  echo "0   /* 0: big ENDIAN, 1: little ENDIAN */" > ../cpu0.config
fi
```

The hex file gets loaded into the Verilog testbench via `$readmemh`, and the simulator executes the program instruction by instruction. The test program exercises every instruction in the ISA and prints expected results to an output port. If any result is wrong, the output differs from the expected baseline.

### Four Configurations

The test runs in all four combinations:

| CPU | Endianness | Key Differences |
|-----|-----------|----------------|
| Cpu032I | Big-endian (`eb`) | CMP-based comparisons |
| Cpu032I | Little-endian (`el`) | CMP-based, reversed byte order |
| Cpu032II | Big-endian (`eb`) | SLT-based comparisons, long branch |
| Cpu032II | Little-endian (`el`) | SLT-based, reversed byte order |

All four configurations must produce identical output. The Cpu032II configuration was where the SetCC_I encoding bug manifested -- it used `SLTi` which Cpu032I doesn't have, so the bug was variant-specific.

### What the Test Programs Cover

The 23 Verilog test programs (compiled to `.hex` and run through the simulator) exercise:

| Category | Programs | What they test |
|----------|---------|----------------|
| Arithmetic | 3 | Integer add/sub/mul, HI/LO multiply, divide |
| Control flow | 4 | If/else, while loop, for loop, switch |
| Function calls | 3 | Leaf function, nested calls, recursion (fibonacci) |
| Pointers & structs | 3 | Array access, struct field access, pointer arithmetic |
| Global variables | 2 | Global int, global array |
| Bit operations | 2 | Shifts, bitwise AND/OR/XOR/NOT |
| Calling conventions | 2 | 3+ argument functions, return struct |
| Stack allocation | 2 | alloca(), variable-length arrays |
| Type conversions | 2 | Signed/unsigned extension, truncation |

The programs are simple (10-50 lines of C each) but comprehensive in their instruction coverage. The simulator counts every instruction executed and can detect infinite loops (if execution exceeds a threshold cycle count).

### What the Simulator Caught That LLVM Didn't

The Verilog simulator provides a fundamentally different kind of verification than LLVM's lit tests:

| Property | LLVM lit tests | Verilog RTL simulation |
|----------|---------------|----------------------|
| Tests instruction selection | Yes (CHECK patterns) | No |
| Tests binary encoding | Indirectly (round-trip) | **Yes** (executes actual bits) |
| Tests instruction semantics | No | **Yes** (cycle-accurate) |
| Tests endianness handling | Partially | **Yes** (reads bytes from memory) |
| Tests instruction interactions | Minimally | **Yes** (full programs) |

The round-trip test (assemble then disassemble) verifies encoding **consistency** but not **correctness**. If both the encoder and decoder agree on a wrong encoding, the round trip passes. Only execution on a model that independently implements the ISA catches encoding errors.

## Reflections: What 12,260 Lines Taught Us

Building the Cpu0 backend from scratch, across 16 commits and all 13 chapters of the tutorial, revealed several architectural insights about LLVM:

### TableGen is the backbone

The `.td` files are small (a few hundred lines for instructions), but they generate the majority of the code. The encoder, decoder, matcher, and printer are all generated from the same definitions. Getting the `.td` right is 80% of the work for any new instruction.

### Custom lowering is where complexity lives

TableGen handles the simple cases beautifully. The hard cases -- global address computation, TLS models, atomic LL/SC loops -- require hand-written C++ in `ISelLowering.cpp`. These custom lowering functions account for the bulk of our 12,260 lines.

### The MC layer provides clean abstraction

The `MCInst` abstraction -- a target-independent instruction representation -- is what makes the assembler, disassembler, and code emitter composable. You can add a new tool (like a binary analysis framework) by consuming `MCInst`, without touching any of the compiler internals.

### Reference implementations have bugs

We found at least two bugs in the reference implementation (XOR-not-NOR for NAND). Blindly copying reference code is dangerous. Every piece of code should be verified against the ISA specification and tested with execution.

### Hardware simulation is irreplaceable

The LLVM test infrastructure is excellent for checking that the compiler produces *expected* output. But it cannot verify that the output is *correct* in the hardware sense. The Verilog simulator found bugs that no amount of FileCheck patterns would catch.

## The Complete Stack

Looking back at the full backend, here's what we built:

| Layer | Lines (approx) | What it does |
|-------|----------------|--------------|
| TableGen (`.td` files) | ~1,600 | Instruction formats, encodings, patterns, registers, scheduling |
| Instruction selection | ~2,500 | DAG lowering, custom nodes, pattern matching |
| Frame/calling convention | ~1,800 | Prologue/epilogue, argument passing, stack layout |
| MC layer | ~2,000 | Code emission, ELF writing, fixups, relocations |
| Assembler/Disassembler | ~1,500 | Assembly parsing, binary decoding |
| Atomics/TLS/EH | ~1,800 | LL/SC loops, TLS models, exception metadata |
| Custom passes | ~800 | Branch expansion, delay slot filling, dead jump removal |
| Verilog test infra | ~600 | RTL model integration, test harness |
| **Total** | **~12,260** | A complete, verified LLVM backend |

Every one of these layers exists for a reason, and understanding why is the real takeaway. LLVM's layering isn't accidental -- it's the result of decades of iteration on compiler design, and it works.
